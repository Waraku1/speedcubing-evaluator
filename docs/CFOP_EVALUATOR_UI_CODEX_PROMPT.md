# Codex実装依頼: CFOP解法・Evaluator連携・UI改善

以下をCodexに渡して実装してください。

## 目的

このリポジトリの既存CFOPソルバーを使い、入力されたキューブ状態に対して次を実現してください。

1. **完全解**: CFOPのCross → F2L → OLL → PLLの手順を段階ごとに表示し、最後にキューブが完成することを確認できる。
2. **部分解**: 利用者が選んだCFOPの到達目標までの手順を表示する。Evaluatorの評価を使って候補を比較し、選んだ候補が目標状態を満たすことを検証する。
3. **Evaluator連携**: 実際に画面へ表示・再生する手順をEvaluatorへ渡し、Evaluatorの結果が同じ手順に対するものだと確認できる。
4. **UI配置改善**: 入力、解法の選択、手順、Evaluator結果、キューブ状態の配置を整理する。現在のプロジェクトの色・文字・パネルの雰囲気を保ち、別テーマへの作り替えはしない。

ここでの「部分解」は、既存実装やテストに別の意味が定義されていない限り、**Cross / F2L / OLL のいずれかを利用者が指定し、その段階を到達目標として止める解法**とします。完全解はPLLまで実行します。部分解は選択された段階より先を解いたように表示せず、キューブ全体が完成したとも表示しないでください。

## 作業開始時の確認

- `feature/generator` 上で作業し、別ブランチへ移動したり、`main` に変更を入れたりしない。
- 既存のユーザー変更があれば保持する。
- 実装前に `src/lib/cfop-solver`、`src/lib/evaluator`、`src/lib/cube`、`src/app`、API、関連テストを読み、実際に呼び出されている関数と型を確認する。

## リポジトリ調査で分かったこと

- CFOPの状態ベース入口は `src/lib/cfop-solver/cfop-solver.ts` の `solveCFOPState(state)`。既存結果には `phases.cross/f2l/oll/pll`、各フェーズの `moves`・`stateBefore`・`stateAfter`、全体の `solution`・手数・`progress` が含まれる。
- `verifySolveResult(result)` は全体解と段階ごとの状態遷移を検証する。`src/lib/cfop-solver/state-adapter.ts` には `URFDLB_FACELETS_V1` 形式と入力状態の検証がある。
- CFOPエンジンは `src/lib/cube/moves.ts` の文字列形式 `CubeState` を使う。別の `src/lib/cube/cube.ts` は面配列のオブジェクト形式 `CubeState` を使う。両者を暗黙に混ぜない。
- 旧Evaluatorの `src/lib/evaluator/legacy/evaluator.ts` に `evaluateMoves(initial, moves)` があり、`normalizedMoves`、`isSolved`、`humanEfficiencyScore` などを返す。
- 新しい `PrototypeEvaluatorPipeline` は `generateTransitions(createInitialHumanState(), moves)` で生成した手順遷移を評価する。これはキューブが部分目標／完成状態に達したかの検証を代替しない。必要ならCFOP側のキューブシミュレーションと組み合わせる。
- `src/app/page.tsx` はNext.jsの初期テンプレート、`src/app/detect/page.tsx` はカメラ検出画面。現時点で `/solver` 画面はなく、`tests/e2e/solver.e2e.ts` は `/solver` の表示を想定している。
- 現在の `src/app/api/solve/route.ts` は仮の `solve()` を呼び、`src/lib/solver/solver.ts` は固定の `R U R'` を返すスタブ。CFOP機能をこのスタブの結果で実装・表示しない。
- このリポジトリには異なるCubeState型と解法経路が存在する。既存画面・API・テストを確認し、同じ処理を二重実装しない。

## 実装要件

### 1. CFOP手順

- 完全解では既存の `solveCFOPState` / facelet adapter を利用し、Cross、F2L、OLL、PLLの順で手順を表示する。
- 部分解では同じCFOP結果の段階データを利用し、選択された到達目標までの手順だけを表示する。F2Lは既存の `f2l.stages` が使えるため、既存のスロット単位情報を損なわない。
- 表示順は実行順と一致させる。全体手順、各段階の手順、現在位置の表示が互いに食い違わないこと。
- 既に目標が達成済み、または入力が解決済みの場合は「目標達成済み」と示し、架空の手順を作らない。
- 不正な54文字入力、色数不整合、物理的に到達不能な状態、ソルバー例外を区別して利用者に分かるエラーとして表示する。

### 2. Evaluatorを使った部分解の最適化

- 「最適化」の評価基準をUI上で明示する。既存Evaluatorの人間工学／実行しやすさのスコアを主基準とし、同点ならHTMが少ない候補を優先する。
- 既存ソルバーのケース表や妥当な候補生成を調べ、**同じ目標を満たす複数の有効候補**が得られる場合にEvaluatorで比較する。候補生成のために別の完全ソルバー、無制限探索、未検証のアルゴリズムを導入しない。
- 候補が1つしか得られない場合は、全体最適・最短解と誤認させない。Evaluator評価済みの手順と、保証できる範囲を正確に表示する。
- 正規化や最適化後に画面へ出す最終手順を、CFOPのキューブ状態シミュレーターで再適用し、選択した目標状態に到達することを必ず検証する。Crossや既に完成しているF2Lスロットを壊さないことも確認する。
- Evaluatorが評価した手順と、画面に表示・再生する手順を一致させる。手順を変更した場合はEvaluatorを再実行する。`normalizedMoves` を採用する場合も、採用後の手順を状態検証し、数値が採用後の手順に対応するようにする。
- Evaluatorスコアを使ってキューブ状態の正しさを推定しない。Evaluator評価とCFOP状態検証をそれぞれ行う。

### 3. 手順の適用・再生確認

- 各ステップにフェーズ名、手順、手数を表示し、前へ／次へで現在ステップと対応するキューブ状態が同期するようにする。
- 各段階で `stateBefore` に段階手順を適用した結果が `stateAfter` と一致することを確認する。
- 完全解では表示手順全体を初期状態へ適用した結果がSolved Stateと一致することを確認する。部分解では選択した目標フェーズの状態と一致することを確認する。
- 「Evaluatorの手順への正しい適用」は、Evaluatorの公開APIに表示対象と同じ `Move[]` を渡したことをテストまたは型安全な共通関数で確認する。入力スクランブルや別フェーズの配列を誤って評価しない。
- CFOPのMove型とEvaluatorのMove型が現状同じ記法・意味であることを確認し、変換が必要なら1箇所の明示的なadapterに閉じ込める。

### 4. 画面と配置

- 現行アプリで実際に使われている画面・配色・コンポーネントを確認してから変更する。既存テーマの色、文字の雰囲気、角丸・境界線・背景のトーンを維持する。
- `/solver` が存在しない場合は、既存画面を壊さず、E2Eテストが想定する `/solver` を実装する。カメラ検出の `/detect` は維持する。
- 入力と実行モード／到達目標を一つのまとまりにし、解法結果は「段階」「現在手順」「全体手順」「Evaluator評価」が視線順に追える配置にする。
- デスクトップでは入力・状態表示と手順結果の領域を無理なく分け、モバイルでは一列に再配置する。狭い幅で横スクロールを起こさない。
- 操作中／計算中／成功／入力エラー／ソルバーエラー／目標達成済みを区別する。日本語UIとキーボード操作可能なボタン・ラベルを用意する。
- テーマを全面刷新したり、要求外のカメラ認識・認証・保存機能を追加したりしない。

### 5. APIと互換性

- 現行 `/api/solve` の実装、関連テスト、呼び出し元を先に確認する。既存利用者がある場合は互換性を保つ。CFOPの入力・モード・到達目標を表せない場合は、既存機能を壊さないAPI拡張または適切な専用routeを選ぶ。
- リクエストの型・必須項目・54文字／色数／到達可能性を検証し、適切な4xxと利用者向けメッセージを返す。予期しないソルバー失敗を成功レスポンスに偽装しない。
- CFOP結果のフェーズ手順、目標、最終検証結果、Evaluator評価対象がUIへ渡る契約を型で表す。

## 受け入れ条件

1. 有効な未解決状態の完全解要求で、Cross / F2L / OLL / PLLの順にCFOP手順が表示され、画面で表示した手順全体を再適用するとSolved Stateになる。
2. Cross / F2L / OLLの部分解要求で、選んだ目標までの手順だけが表示され、再適用後に目標を満たす。未完了なのに完全解済みと表示しない。
3. 部分解のEvaluator評価対象が実際に画面に表示する手順と一致する。評価後の手順変更がある場合は再評価される。
4. 最適化候補が複数ある場合、同じ目標を満たす候補だけを比較し、採用候補の有効性を再検証する。グローバル最短など保証できない主張をしない。
5. 既に達成済みの目標とSolved Stateでは空手順を正しく扱う。不正入力・到達不能状態・失敗を適切に表示する。
6. F2L段階ごとの既存の保護条件（Crossと完了済みスロットを壊さない）を保つ。
7. `/solver` を開け、モバイル幅でも主要操作と結果を使え、横スクロールが発生しない。既存の `/detect` を壊さない。
8. 変更対象を必要な範囲に絞り、`src/lib/cube/moves.ts` はキューブ基盤の正しさに関わるため、修正が不可欠である根拠と回帰テストがない限り変更しない。
